# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Deliver a professional, responsive, end-user ticketing interface for Requesters with strict data isolation, temporary development requester context switching, clear validation standards, attachment lifecycle management, and robust error recovery compliant with Zen Green Theme design conventions.

## 2. Stakeholder Request Interpretation
The IT department needs a functional Requester module allowing users to:
- Submit tickets with metadata, clear descriptions, priority selection, and attachments.
- Manage tickets through a dedicated "My Tickets" list with search, filtering, sorting, and pagination.
- Inspect ticket details and manage attachments (soft removal with rationale).
- Ensure strict ownership isolation (users cannot access other users' tickets).
- Provide a Development Requester Selector as a placeholder identity switch until Sprint 3 authentication.

## 3. Scope
### Included
- Development Requester Selection Screen & context header component.
- Create Ticket form with client/server validation and state preservation on failure.
- Attachment uploading (JPG/PNG/WEBP/PDF, ≤5MB, max 5 active attachments).
- My Tickets list view with search, status/priority/category filters, sorting, and pagination.
- Ticket Detail view with attachment preview/download and soft removal with reason capture.
- Standardized UI component states (Loading, Empty, No-Results, Failure/Error, Validation, Responsive Layout, Keyboard Accessibility).

### Excluded
- Real Authentication (SSO/JWT/Passwords) — Deferred to Lab 3.
- IT Staff Dashboard / Ticket Queue view.
- Internal Notes, Comments, or SLA assignment workflows.
- Ticket status transition by Requester (Status defaults to `New` and is immutable in Lab 2).
- Administrative capabilities (category creation, system configuration).

## 4. Functional Requirements
- **FR-01**: The system shall allow selecting an active Requester from a development selection screen to establish testing context.
- **FR-02**: The system shall generate a unique official Ticket Number upon successful submission.
- **FR-03**: The system shall enforce ticket ownership so Requesters only view and interact with their own tickets.
- **FR-04**: The system shall support filtering, searching, sorting, and paginating tickets on the My Tickets screen.
- **FR-05**: The system shall support attachment uploads adhering to strict format, size, and quantity limits.
- **FR-06**: The system shall support soft removal of attachments requiring user confirmation and reason input.
- **FR-07**: The system shall preserve form input data when backend API submission fails to allow safe retry without data loss.

## 5. Business Rules
- **BR-01**: The official Ticket Number is generated by the backend and must be unique (e.g., `TICK-YYYYMMDD-XXXX`).
- **BR-02**: A new Ticket begins with Current Status `New`.
- **BR-03**: Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication.
- **BR-04**: Only active Requesters (`isActive = true`) are loaded into the selector dropdown. Inactive Requesters must be excluded.
- **BR-05**: Strict ownership isolation: Requesters can only access, view, or search tickets where `requesterId` matches their active session context. Cross-requester viewing or unowned ticket requests must consistently return HTTP `404 Not Found` to avoid leaking ticket existence.
- **BR-06**: Input Validation: Ticket Summary is required (min 5, max 100 chars). Description is required (min 10, max 2000 chars). Category and Related System choices are mandatory. Leading/trailing whitespace must be trimmed automatically.
- **BR-07**: Attachment Rules: Allowed file types are `JPG`, `JPEG`, `PNG`, `WEBP`, and `PDF`. Maximum file size is 5 MB per file. Maximum active (non-removed) attachments per ticket is 5.
- **BR-08**: Soft Removal: Attachment deletion is executed via soft removal (`isRemoved = true`). File metadata remains visible in history, but binary download and preview endpoints must be disabled.
- **BR-09**: Removal Rationale: Soft removal requires user confirmation and a mandatory removal reason (min 5, max 250 chars).
- **BR-10**: Duplicate Submission & Idempotency: UI submit buttons must enter a disabled busy state upon submission. The backend must reject a new ticket submission if an identical payload (same `requesterId`, `summary`, and `description`) was submitted by the same requester within the last 5 seconds, to prevent duplicate ticket records.
- **BR-11**: Failure Recovery & Data Retention: If ticket creation or network request fails (e.g., backend offline or validation error), the UI must display a clear error state while keeping all user-entered form fields intact for correction and resubmission.
- **BR-12**: Attachment Upload Compensation Strategy: Ticket metadata creation and file upload execute as a coordinated transaction. If ticket creation succeeds but an associated attachment upload fails, the server rolls back ticket creation (or marks upload incomplete) and alerts the user to retry without losing form input.
- **BR-13**: Search, Filter, Sort & Pagination Standard: Default sorting order for My Tickets is `createdAt DESC` (newest first). Search queries evaluate against `ticketNumber`, `summary`, and `description`. Default page size is 10 items per page with explicit page navigation controls.

## 6. UI Specification Summary
- **Design Theme**: Zen Green Theme (Primary `#006B3C`, Hover `#0B7A46`, Pale background `#EAF6EF`).
- **Layout**: Fully responsive design supporting Desktop (≥1024px), Tablet (768px–1023px), and Mobile (<768px).
- **Reusable States**: Standardized presentation for Loading Skeletons, Empty Lists, No Search Results, Field Validation Errors, System Error Banners with state preservation, and Keyboard Accessibility focus styling.

## 7. Data Changes
Models to be added/updated in Prisma Schema:
- `RequesterUser`: Identity entity (`id`, `name`, `email`, `department`, `isActive`).
- `Category`: Categorization entity (`id`, `name`, `code`, `isActive`).
- `RelatedSystem`: Target system entity (`id`, `name`, `code`, `isActive`).
- `Ticket`: Core entity (`id`, `ticketNumber`, `summary`, `description`, `requestedPriority`, `status`, `requesterId`, `categoryId`, `relatedSystemId`, `createdAt`, `updatedAt`).
- `Attachment`: File relation entity (`id`, `ticketId`, `fileName`, `fileSize`, `fileType`, `filePath`, `isRemoved`, `removalReason`, `createdAt`).

## 8. API Contract Summary
- `GET /api/requesters` - List active requesters for testing selector.
- `GET /api/categories` - Retrieve active Categories list for ticket forms.
- `GET /api/related-systems` - Retrieve active Related Systems list for ticket forms.
- `POST /api/tickets` - Submit new ticket with metadata and optional attachments.
- `GET /api/tickets` - Fetch paginated user tickets with search, status, priority, and category filters.
- `GET /api/tickets/:id` - Fetch single ticket detail (enforcing requester ownership).
- `POST /api/tickets/:id/attachments` - Upload additional attachment to existing ticket.
- `GET /api/tickets/:id/attachments/:attachmentId` - Retrieve single Attachment metadata.
- `GET /api/tickets/:id/attachments/:attachmentId/download` - Download active Attachment file content.
- `DELETE /api/tickets/:id/attachments/:attachmentId` - Soft-remove attachment with removal reason.

## 9. Acceptance Criteria
- **AC-01**: Given an active selected Requester, When submitting a valid Create Ticket form, Then a unique Ticket Number is generated, status is set to `New`, and the ticket appears in My Tickets.
- **AC-02**: Given an active Requester context, When viewing My Tickets or searching/filtering, Then only tickets created by that specific Requester ID are returned.
- **AC-03**: Given a file larger than 5 MB or invalid extension (e.g., .exe), When attaching to a ticket, Then the form validation blocks submission with a clear error message.
- **AC-04**: Given an attached active file on a ticket, When the Requester performs a soft removal with a valid reason, Then `isRemoved` becomes true, metadata is kept, and download/preview buttons are disabled.
- **AC-05**: Given an inactive Requester record in the DB, When fetching the Development Requester list, Then that inactive user does not appear in the selection dropdown.
- **AC-06**: Given a search query or filter parameters on My Tickets, When applied, Then the ticket list re-paginates and displays matching results sorted by `createdAt DESC` by default.
- **AC-07**: Given a change in the active Development Requester selection context, When switched, Then the My Tickets list automatically clears and refreshes to reflect tickets belonging strictly to the newly selected Requester.
- **AC-08**: Given a Requester with zero submitted tickets, When opening My Tickets, Then an "Empty State" container is displayed; When filters yield zero results, Then a "No-Results State" container with a filter reset action is displayed.
- **AC-09**: Given a network failure or backend error during ticket submission, When submission fails, Then a prominent error message is displayed and all typed form input values remain preserved.
- **AC-10**: Given any screen in the Requester module, When tested across Mobile, Tablet, and Desktop viewports, Then all interactive components resize fluidly without broken horizontal layouts.
- **AC-11**: Given keyboard navigation (Tab/Shift+Tab/Enter), When navigating ticket forms and attachment modals, Then all inputs, options, and actions have visible focus indicators and are fully accessible without a mouse.

## 11. Assumptions and Decisions
- **Field Constraints**: Ticket Summary constrained to 5–100 characters; Description constrained to 10–2000 characters.
- **Pagination Defaults**: Default page size set to 10 tickets per page.
- **Attachment Storage**: Files stored on server local disk with generated UUID filenames to prevent file collision and execution.
- **Database Design Decision (Indexing)**: A composite index `(requester_id, created_at DESC)` must be created on the `Ticket` database table. *Justification*: Queries on "My Tickets" filter strictly by `requesterId` and default to sorting by newest `createdAt`. A composite index guarantees $O(\log N)$ query speed and avoids costly in-memory filesort operations during database pagination.
